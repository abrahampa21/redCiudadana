 2. VULNERABILIDADES DE SEGURIDAD
================================================================================

 2.1  CONTRASENAS CON SHA-1 (GRAVE)
 ──────
 Archivos: index.php:42, loginAdmin/index.php:42
           src/api/usuarios_api.php:41 (envia hash SHA-1)
 Problema: SHA-1 es criptograficamente roto desde 2005. Se puede
           romper en segundos con hardware moderno (8,000 millones
           de hashes/segundo en GPU). Cualquier filtracion de la BD
           expone todas las contrasenas en texto plano inmediato.
 Riesgo:   ALTO - Exposicion total de credenciales de usuarios.
 Solucion: Usar password_hash($pass, PASSWORD_BCRYPT) para
           almacenar y password_verify() para verificar.

 2.2  CORS CON WILDCARD (*) EN TODAS LAS APIS
 ──────
 Archivos: src/api/reportes_api.php:5
           src/api/evidencias_api.php:4
           src/api/usuarios_api.php:4
 Problema: Access-Control-Allow-Origin: * permite que CUALQUIER
           sitio web externo haga peticiones AJAX a las APIs.
           Un atacante puede crear un sitio malicioso que robe
           datos de usuarios autenticados (CSRF via CORS).
 Riesgo:   ALTO - Robo de informacion y suplantacion.
 Solucion: Restringir a origenes especificos o validar tokens.

 2.3  SIN PROTECCION CSRF EN FORMULARIOS //HACER ESTO SOLO HASTA EL FINAL Y PERMITIR SOLO LOCALHOST
 ──────
 Archivos: index.php (registro/login), loginAdmin/index.php,
           panelCiudadano/nuevoReporte.php
 Problema: Ningun formulario incluye un token CSRF. Cualquier
           sitio externo puede enviar peticiones POST al servidor
           y crear cuentas o reportes en nombre de usuarios.
 Riesgo:   ALTO - Creacion fraudulenta de cuentas y reportes.
 Solucion: Implementar tokens CSRF unicos por sesion.

 2.4  SESION SIN TIMEOUT NI REGENERACION DE ID
 ──────
 Archivos: Todos los que usan session_start()
 Problema: No se configura session.gc_maxlifetime, ni se regenera
           el session_id() despues del login. La sesion dura
           indefinidamente y es vulnerable a session fixation.
 Riesgo:   MEDIO - Secuestro de sesion.
 Solucion: Configurar tiempo de expiracion y llamar
           session_regenerate_id(true) despues del login.

 2.5  INFORMACION DEL SERVIDOR EN RESPUESTAS DE ERROR
 ──────
 Archivos: src/api/reportes_api.php:104
           src/api/evidencias_api.php:67
           src/api/usuarios_api.php:52
           loginAdmin/index.php:107
 Problema: Las APIs devuelven $stmt->error y $conn->error en las
           respuestas JSON, exponiendo estructura interna de la
           base de datos (nombres de tablas, columnas, etc.).
 Riesgo:   MEDIO - Fuga de informacion para ataques dirigidos.
 Solucion: Loggear el error internamente y devolver mensaje
           generico al usuario.

 2.6  SIN HTTPS FORZADO
 ──────
 Archivos: Ninguno
 Problema: No hay redireccion de HTTP a HTTPS. Las contrasenas
           viajan en texto plano por la red si no se usa HTTPS.
 Riesgo:   ALTO - Intercepcion de credenciales (man-in-the-middle).
 Solucion: Forzar HTTPS via .htaccess o configuracion del servidor.

 3. PROBLEMAS DE BACKEND (PHP Y BASE DE DATOS)
================================================================================

 3.1  QUERIES SIN LIMIT NI PAGINACION
 ──────
 Archivos: src/api/reportes_api.php:69
           src/api/evidencias_api.php:34
           src/api/usuarios_api.php:16
 Problema: "SELECT * FROM reporte" sin LIMIT ni paginacion. Con
           miles de registros, el servidor se queda sin memoria,
           la respuesta es lentisima, y el frontend se congela.
 Solucion: Implementar paginacion con LIMIT y OFFSET, o cursor-
           based pagination.

 3.2  CONEXION CERRADA DENTRO DEL SWITCH
 ──────
 Archivo: src/api/reportes_api.php:30,47,64
          src/api/evidencias_api.php:29
 Problema: $conn->close() se ejecuta dentro de los if-else del
           switch. Si caen en un caso que no ejecuta close(), o
           si hay mas de una operacion, la conexion se cierra
           prematuramente. Ademas, $conn ya no existe para el
           resto del script.
 Solucion: Mover $conn->close() fuera del switch, al final.

 3.3  NOMBRE INCONSISTENTE DE COLUMNA EN CATEGORIAS
 ──────
 Archivo: panelCiudadano/nuevoReporte.php:68 ✅HECHO
 Codigo:  $categoria['id']
 Problema: La consulta SQL hace "SELECT id_categoria, nombre FROM
           categoria", pero el foreach accede a $categoria['id'].
           La key correcta es 'id_categoria'. Esto genera errores
           de indice indefinido.
 Solucion: Cambiar $categoria['id'] por $categoria['id_categoria'].

 3.4  FORMULARIO SIN ENCTYPE PARA SUBIR ARCHIVOS ✅HECHO
 ──────
 Archivo: panelCiudadano/nuevoReporte.php:44
 Problema: El formulario tiene <input type="file"> pero NO tiene
           enctype="multipart/form-data". Los archivos jamas se
           envian al servidor.
 Solucion: Agregar enctype="multipart/form-data" al tag <form>.

 3.5  ACTION DEL FORMULARIO SIN EXTENSION .PHP
 ──────
 Archivo: panelCiudadano/nuevoReporte.php:44
 Codigo:  action="handler/nuevoReporteCiudadano"
 Problema: El action apunta a un archivo sin extension .php.
           Dependiendo de la configuracion del servidor, esto
           devuelve 404 o descarga el archivo como texto.
 Solucion: Cambiar a action="handler/nuevoReporteCiudadano.php".

 3.6  SIN VALIDACION DE TIPO Y TAMANO DE ARCHIVO
 ──────
 Archivo: panelCiudadano/nuevoReporte.php:80
          panelCiudadano/handler/nuevoReporteCiudadano.php
 Problema: No se valida extension, tipo MIME ni tamano maximo del
           archivo de evidencia. Un atacante puede subir .php o
           .exe, comprometiendo el servidor.
 Solucion: Validar extension (solo jpg,png,gif,webp), tipo MIME,
           y establecer limite de tamano (ej: 5MB).

 3.7  DUPLICACION DE LOGICA DE AUTENTICACION
 ──────
 Archivos: index.php y loginAdmin/index.php (codigo casi identico)
 Problema: La logica de registro, login y recuperacion de
           contrasena esta duplicada en ambos archivos. Si se
           cambia algo en uno, hay que acordarse de cambiarlo
           en el otro. Violacion del principio DRY.
 Solucion: Unificar en una sola clase/controlador de autenticacion
           que reciba el rol como parametro.

 3.8  SIN TRANSACCIONES EN OPERACIONES MULTIPLES
 ──────
 Archivo: src/api/reportes_api.php (POST)
 Problema: Crear un reporte requiere insertar en tabla reporte y
           posiblemente en evidencias. No se usa transaccion
           ($conn->begin_transaction()). Si falla el segundo
           INSERT, queda un reporte huerfano.
 Solucion: Usar transacciones MySQLi para operaciones atomicas.

 3.9  MANEJO INSEGURO DE ARCHIVOS DE EVIDENCIA
 ──────
 Archivo: src/api/evidencias_api.php:53-60
 Problema: $id_reporte viene de $_GET pero se pasa directo al
           bind_param sin validar que el reporte pertenezca al
           usuario. Cualquier usuario puede adjuntar evidencias
           a reportes de otros.
 Solucion: Validar que el reporte pertenezca al usuario en sesion.

 3.10  COALESCE/NULLIF INNECESARIO EN UPDATE
 ──────
 Archivos: src/api/reportes_api.php:124
           src/api/usuarios_api.php:44
 Codigo:   UPDATE ... SET columna = COALESCE(NULLIF(?, ''), columna)
 Problema: $id_estado es un entero (intval). NULLIF(?, '')
           compara un entero con string '', lo cual siempre es
           verdadero (entero != ''), asi que COALESCE siempre
           devuelve el valor nuevo. La proteccion no funciona.
 Solucion: Simplificar: SET id_estado = ? y validar el dato
           antes de ejecutar la consulta.

 3.11  SIN INDEXS EN LA BASE DE DATOS
 ──────
 Archivos: Las consultas SELECT * FROM reporte WHERE id_categoria = ?
           etc. No hay sugerencias de indices en el esquema.
 Problema: Sin indices en id_categoria, id_estado, id_prioridad,
           id_usuario, las consultas hacen full table scan.
           Con miles de reportes, las consultas seran lentisimas.
 Solucion: Agregar indices compuestos en las columnas de filtrado.

 3.12  SIN CACHE DE NINGUN TIPO
 ──────
 Archivos: Todas las APIs
 Problema: Cada peticion GET consulta la BD aunque los datos no
           hayan cambiado. Sin cache (Redis, Memcached, o incluso
           cache de opcode), el servidor se satura facilmente.
 Solucion: Implementar cache con TTL para datos de consulta
           frecuente (categorias, estados, estadisticas).

 3.13  HEADERS CORS DUPLICADOS Y PERMISIVOS EN METHODS
 ──────
 Archivos: src/api/reportes_api.php:7
           src/api/evidencias_api.php:6
           src/api/usuarios_api.php:6
 Problema: Access-Control-Allow-Methods lista PUT, PATCH, DELETE
           incluso en endpoints que no los implementan. PUT y
           PATCH tienen cases vacios (break sin hacer nada).
           Esto es confuso y potencialmente inseguro.
 Solucion: Solo permitir los metodos que realmente se implementan.

 Archivo: loginAdmin/index.php:105

 3.15  ELIMINACION DE REPORTES SIN VERIFICACION DE PROPIEDAD

 5. CONSUMO DE RECURSOS (PROYECCION A FUTURO)
================================================================================

 5.1  ESCALABILIDAD
 ──────
 Problemas identificados:
 - SELECT * sin LIMIT: Con 10,000 reportes, la API devuelve
   ~5-10MB de JSON. Tiempo de respuesta >5 segundos.
 - Sin paginacion: El frontend recibe TODO de golpe.
 - Sin indices en BD: Full table scans en cada consulta.
 - Sin cache: Cada request golpea MySQL directamente.
 - Sesiones en archivos: No escalan horizontalmente.
 Proyeccion: Con 100 usuarios concurrentes y 5,000 reportes,
             el servidor se satura en menos de 1 minuto.

 5.2  MEMORIA
 ──────
 - El SELECT * sin LIMIT puede agotar la memoria de PHP
   (memory_limit tipico 128MB) con ~20,000 registros.
 - node_modules (300MB+) en produccion es desperdicio total.
 - Las sesiones en archivos en disco pueden llenar el
   almacenamiento con miles de usuarios.

 5.3  RENDIMIENTO
 ──────
 - FontAwesome + Bootstrap = ~230KB de JS innecesario.
 - 4 hojas de CSS separadas = 4 HTTP requests adicionales.
 - Google Fonts DM Sans es otro request externo.
 - Sin HTTP/2, cada recurso externo suma latencia.

 5.4  SEGURIDAD
 ──────
 - SHA-1: Cualquier filtracion de BD expone todas las
   contrasenas inmediatamente.
 - Sin rate limiting: Fuerza bruta ilimitada.
 - Sin CSRF: Ataques de cross-site request forgery.
 - CORS abierto: Exfiltracion de datos desde cualquier sitio.
